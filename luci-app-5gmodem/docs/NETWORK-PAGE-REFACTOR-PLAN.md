# План рефакторинга страницы «Сеть» (для Опуса)

Цель: страница открывается **мгновенно** (skeleton сразу, данные подтягиваются
прогрессивно), опрос модема — быстрый и модульный, парсинг унифицирован, легко
добавлять новые модемы. Ниже — измеренная диагностика, целевая архитектура и
пошаговый план с конкретными файлами.

---

## 0. Как устроено сейчас (факты из кода)

**Точки входа:**
- View: `htdocs/luci-static/resources/view/modem/5gdetail.js` — монолитный
  `view.extend({ load, render })` (~2300 строк) + `poll.add` каждые 5 c.
- Данные модема: `root/usr/share/5gmodem/5gmodem.sh json` — один большой скрипт,
  который источает **per-VIDPID профиль** `root/usr/share/5gmodem/modem/usb/<vidpid>`
  (их **61 штука**, 0.7–16 КБ каждый), каждый со своими AT/QMI/mmcli-командами и
  парсингом, выставляющий шелл-переменные (MODE, RSRP, PBAND, S1BAND, TAC…),
  которые главный скрипт печатает в JSON.
- Ещё скрипты: `bands.sh` (бэнды/режимы), `netpri.sh` (приоритет WAN),
  `simslot.sh` (SIM/eSIM слоты), `esim.sh` (lpac), `detect.sh` (AT-порт),
  `listmodems.sh`, `modemswitch.sh` (активный модем/mmindex/wdm), `ttl.sh`.

**Поток загрузки (главная проблема):**
`load()` в 5gdetail.js **БЛОКИРУЕТ render()** пока не вернётся:
```
modemswitch.sh mmindex           # последовательно
  -> Promise.all([ 5gmodem.sh json,  mmcli -m <idx> -K,  uci.load,  ttl.sh get ])
```
Пока это не завершилось — **страница пустая**. Параллельно на открытии ещё
стартуют `modemtabs.attach()` (listmodems + modemswitch active) и `netpri`
(netpri.sh list) — 5–6 процессов разом конкурируют за AT-порт/mmcli.

**Измерено (Hiveton, Compal RXM-G1, MBIM/ModemManager):**
| вызов | холодный | тёплый |
|---|---|---|
| `5gmodem.sh json` | **13 c** | ~1 c |
| весь бурст открытия | **12 c** | — |
| `detect.sh` | 8 c | 0 c |
| `bands.sh json` | 4.2 c | 4.2 c |
| одиночная AT/mmcli/qmicli | <0.2 c | <0.2 c |

**Где 13 c (профилировано /proc/uptime):**
1. `detect.sh` cold = **8 c**: при `auto_port` без пиннинга `at_port` перебирает
   ttyUSB0/1/2 через `atprobe.sh`, а тот ждёт **4 c** на каждом молчащем
   DIAG/NMEA-порту (`atprobe.sh` cap = 4 c). detect зовётся несколько раз.
2. Статичные AT-поля (модель/IMEI/прошивка/ICCID) при холодном кэше — ~2–3 c.
3. Монолитный профиль парсит ВСЁ за раз (сота, сигнал, CA, бэнды).
4. Блокирующая `load()` показывает всё это как «13 c пустой страницы».

Тёплый путь уже ускорен в этой сессии (кэш порта `[ -c ]` вместо atprobe;
`at_static` кэш статики; `bands.sh` пропускается при свёрнутом блоке). Но
**cold-first-open = 13 c** и **блокирующий render** остаются.

## 1. Целевая архитектура (принципы)

1. **Render-first, никогда не блокируем отрисовку данными.** `load()` возвращает
   почти сразу (только дёшево-статичное: список модемов, конфиг). `render()`
   рисует **скелет** со «спиннерами»/прочерками. Данные приходят опросом и
   заполняют DOM. Пустой страницы 13 c быть не должно — максимум скелет + «…».
2. **Быстрое ядро + ленивые детали.** Разделить данные на:
   - **core** (identity: имя/оператор/SIM, сигнал %, режим, IP, статистика,
     соединение) — цель <1 c даже холодно, опрашивается всегда;
   - **cell** (MCC/MNC, Cell ID, TAC/LAC, RSRP/RSRQ/SINR/RSSI, PCC-бэнд) — только
     когда блок «Информация о соте» раскрыт;
   - **ca** (агрегация по компонентам, MIMO/mod) — только когда раскрыт блок CA;
   - **bands** (`bands.sh`) — только когда раскрыт блок «Управление частотами».
   (Сворачиваемые блоки + модульный опрос уже частично внедрены в 5gdetail.js:
   `collapsibleSection`, `blockExpanded`, `onBlockExpand`, `WANT_SIGNAL/WANT_CA`.
   Нужно довести до конца — см. шаги.)
3. **Унифицированный слой модема (adapter).** Вместо 61 монолитного профиля —
   один общий core-парсер (работает для ~всех через стандартные `AT+CSQ`,
   `+COPS`, `+CxREG`, `+CGCONTRDP`, `AT+CGSN/CGMM/CGMR`, и/или mmcli/qmi) + **тонкие
   адаптеры** только на то, что реально различается (детальные сота/CA/бэнды).
   Явно задать контракт «что адаптер обязан выставить».
4. **Персистентный кэш и пиннинг.** `at_port` пиннить в uci (переживает ребут) —
   убирает cold-detect 8 c. Статику (модель/IMEI/FW/ICCID) кэшировать (уже есть
   `at_static`). Оператор кэшировать (`/tmp/5gmodem_op_<iface>`, уже есть).
5. **Один источник данных на опрос.** Убрать дублирующие вызовы (сейчас
   `5gmodem.sh json` дёргается и в `load()`, и в `poll`, и `mmcli -K` в нескольких
   местах; `ifstatus` звался ~6 раз — уже свёл к 1–2). Кэш общий между
   netpri/simslot/detect.

## 2. Пошаговый план (что и где переписать)

### Шаг 1 — Убить cold-detect (самый большой выигрыш, низкий риск)
Файл: `root/usr/share/5gmodem/detect.sh`, `root/etc/hotplug.d/usb/71-5gmodem-resolve`.
- После первого успешного определения AT-порта **пиннить его в uci**
  (`5gmodem.@5gmodem[0].at_port=<tty>` для одиночного; `m_<path>.at_port` для
  мульти) + `commit`. Тогда detect берёт быстрый путь (строки «at_port pinned»)
  и `atprobe` DIAG-портов не выполняется вообще.
- `atprobe.sh`: снизить cap с 4 c до ~1.5 c (реальный AT-порт отвечает <0.3 c;
  1.5 c достаточно), и **параллелить** пробу кандидатов (запускать atprobe на все
  ttys разом, брать первый ответивший) — cold-scan с 8 c до ~1.5 c.
- Валидацию кэша порта уже сделали через `[ -c "$CP" ]` (без atprobe) — оставить.
Ожидаемо: cold detect 8 c → <1.5 c, и после первого пиннинга — 0 c навсегда.

### Шаг 2 — Render-first во view (убрать блокировку)
Файл: `htdocs/luci-static/resources/view/modem/5gdetail.js`.
- `load()`: вернуть ТОЛЬКО дёшевое — `uci.load('5gmodem')`, `listmodems.sh`
  (0 c). **Не** звать здесь `5gmodem.sh json` / `mmcli -K` / `ttl.sh`.
- `render()`: нарисовать полный скелет (шапка с «—»/спиннером, свёрнутые блоки),
  СРАЗУ вернуть DOM. Затем `poll.add(fetchCore)` — первый опрос заполнит данные.
- `mmIdx`: получать в фоне (не блокируя). До получения `mmcli`-путь бэндов просто
  не активен (бэнды всё равно ленивые).
- Итог: страница появляется мгновенно (скелет), реальные данные — через ~1 c
  (первый core-опрос), без «13 c пустоты».

### Шаг 3 — Разделить бэкенд на секции (модульный опрос)
Файл: `root/usr/share/5gmodem/5gmodem.sh` + профили + view.
- `5gmodem.sh json <sections>` уже принимает список и экспортит `WANT_SIGNAL/
  WANT_CA` (сделано в этой сессии, но профили их пока не читают, а view не
  передаёт). Довести:
  - View `pollData`: формировать sections = `core` + (`cell` если раскрыт блок
    «Информация о соте») + (`ca` если раскрыт CA). Передавать в `5gmodem.sh json`.
  - Профили: обернуть детальные сота/CA/бэнд-запросы в `[ "$WANT_SIGNAL" = 1 ]` /
    `[ "$WANT_CA" = 1 ]`. Осторожно: `MODE` (режим для шапки) часто выводится из
    тех же данных, что и сигнал (GTCCINFO/qmi) — для core вычислять облегчённый
    режим (из mmcli `access-technologies` / `+COPS AcT` / `+CxREG AcT`), а полную
    соту/бэнды — только по запросу секции.
  - `onBlockExpand['cell'|'ca']` — при раскрытии дёрнуть внеочередной опрос с
    нужной секцией (сейчас так сделано только для `freq`/bands).
- `bands.sh` (4.2 c) — уже ленивый (по раскрытию `freq`). Дополнительно
  профилировать его 4 mmcli и кэшировать список поддерживаемых бэндов (статичен
  для модема).

### Шаг 4 — Унифицированный слой модема (главный, но декомпозируемый)
Директории: `root/usr/share/5gmodem/modem/usb/*` (61 профиль).
- Определить **явный контракт адаптера** (документ + пример): какие переменные
  обязан выставить (MODE, PBAND/PCI/EARFCN, RSRP/RSRQ/SINR/RSSI, TAC/CID/LAC,
  S1..S4BAND/PCI/EARFCN/MIMO/MOD, TEMP, MODEL/FW/IMEI/ICCID) и по каким секциям.
- Написать **общий core-модуль** `modem/common/core.sh`, который покрывает
  большинство модемов стандартными командами:
  - identity: `AT+CGMM/CGMI/CGMR/CGSN` (через `at_static`), или mmcli
    `modem.generic.model/revision`, `3gpp.imei`;
  - сигнал %: `AT+CSQ`/`+CESQ` или mmcli `signal-quality`;
  - режим (лёгкий): mmcli `access-technologies` / `+COPS,AcT` / `+CxREG AcT`;
  - IP/DNS: `+CGCONTRDP`/`+GTDNS` или netifd `ifstatus`.
- Профиль сводится к **тонкому адаптеру**: указывает транспорт (AT/mmcli/qmi),
  и переопределяет только детальные `parse_cell()` / `parse_ca()` / `parse_bands()`
  там, где вендор нестандартен (напр. FM350 GTCCINFO/GTCAINFO, Compal qmicli,
  Foxconn `at^debug?`). Общие модемы (Quectel/SIMCOM/Telit со стандартными
  `+QCAINFO`/`+CESQ`) обслуживает core без своего кода.
- Ввести **семейства**: `modem/common/_at_3gpp.sh`, `_qmi.sh`, `_mmcli.sh`,
  `_fibocom.sh`, `_quectel.sh`, `_simcom.sh` — профиль лишь `. _<family>.sh` +
  1–2 переопределения. 61 файл → ~6 семейств + тонкие стабы.
- Миграцию делать **инкрементально**: сначала core + семейство для одного класса
  (напр. Quectel), проверить на живом модеме, затем переносить остальные, оставляя
  старый профиль как fallback, пока новый не подтверждён.

### Шаг 5 — Убрать дубли и контенцию
- Один `5gmodem.sh json` на опрос (не в load и poll одновременно) — следствие
  Шага 2.
- `mmcli -m <idx> -K` кэшировать на ~1 опрос и переиспользовать (сейчас зовётся в
  load, в loadBands, в updateModeButtons, в профиле — 3–4 раза).
- `netpri`/`simslot`/`detect` читают общий кэш порта/оператора (частично есть).
- Убедиться, что параллельные вызовы не бьются об один AT-порт: core через один
  путь (mmcli для MM-модемов, AT-батч для kernel-proto), детали — по запросу.

### Шаг 6 — Скелет и «нет данных без задержек»
- В `render()` все значения — с плейсхолдером `—`/спиннером; первое заполнение по
  core-опросу. Никаких `display:none`-блоков, которые схлопываются позже (это уже
  чинили — сохранить стабильную высоту, см. `collapsibleSection`, липкий `#mode`,
  фикс-строки CA-таблицы).
- Индикатор «обновление…» в углу вместо блокировки.

## 3. Приоритеты и ожидаемый эффект
1. Шаг 1 (пиннинг at_port + быстрый atprobe): cold 13 c → ~4 c, повторные → ~1 c.
   **Низкий риск, огромный выигрыш.**
2. Шаг 2 (render-first): воспринимаемая задержка → ~0 (скелет мгновенно), данные
   ~1 c. **Средний риск (переработка load/render), огромный UX-выигрыш.**
3. Шаг 3 (секции): опрос свёрнутой страницы = только core (~1 c), детали по клику.
4. Шаг 4 (унификация): поддерживаемость + основа для новых модемов; парсинг один,
   а не 61 разный. **Большой, но декомпозируемый; делать инкрементально.**
5. Шаги 5–6: полировка, устранение остаточной контенции и скачков.

## 4. Что НЕ ломать (уроки этой сессии)
- Kernel-proto модемы (FM350) прячутся от ModemManager через `mm-inhibit`; их
  core — AT-батч, не mmcli. MM-модемы (Compal) — mmcli/qmicli.
- FM350 склонен к USB-переперечислению (порты кочуют) — кэш порта должен
  инвалидироваться по исчезновению tty; пустой eSIM вызывает флап.
- `ifstatus` читать один раз; IP брать через `ip -4 addr show dev <l3>` +
  fallback на `<iface>_4`; `"up": false` = нет соединения (не баг).
- Оператор у MBIM/QMI часто только числовой COPS → mccmnc.dat; кэшировать имя.
- В РФ проверять связь по Яндексу (77.88.8.8), не Google.
- Русская локализация: `.lmo` КОММИТИТСЯ в `root/usr/share/5gmodem/i18n/`.
