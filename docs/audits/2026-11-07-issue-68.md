# Issue #68: TD Tech USB configuration and network driver

## New evidence

[The reporter's new capture](https://github.com/fildunsky/luci-app-5gmodem/issues/68#issuecomment-6700237399) shows two configurations for 3466:3301:

| Configuration | Interfaces |
| --- | --- |
| 1 (active, sysfs names `1-8:1.*`) | Four serial interfaces, all bound to `option`; no network function |
| 2 (descriptor only) | Network function on interface 0 (`ff/02/16`, alternate setting 1 carries bulk data), placeholder interface 1, four serial interfaces 2–5 |

The PCUI interface is `ff/06/12`. `AT^SETMODE?` returned the bare value `4`; this is not the USB configuration number and its meaning is not established by this capture.

The absence of a network interface in configuration 1 is confirmed. Successful binding and traffic in configuration 2 are not yet tested.

## Driver implications

Linux 6.12's [huawei_cdc_ncm](https://github.com/torvalds/linux/blob/v6.12/drivers/net/usb/huawei_cdc_ncm.c) recognizes Huawei's `ff/02/16` layout, but its static matches require vendor 12d1. TD Tech's vendor is 3466, so the upstream table does not match it automatically. This makes that driver a candidate, not a confirmed working driver for this modem.

The generic match in [cdc_ncm](https://github.com/torvalds/linux/blob/v6.12/drivers/net/usb/cdc_ncm.c) requires the standard communications/NCM interface class. It does not automatically cover this vendor-specific layout.

The app's current `option` dynamic ID only filters class `ff`, which includes the network interface in configuration 2. `_rescue_data` has no TD Tech case. Merely adding `pick_config ... 2` could expose the network function and then bind it to the wrong driver. A runtime fix needs configuration selection and network-port protection together, with a tested network driver. A working network function must also be preserved across repeated coldplug calls and module re-enumeration.

Before implementation, obtain the installed driver/module aliases from the reporter. Then prepare a controlled configuration-2 binding test with rollback to the captured configuration 1, preserving the PCUI AT port. Check whether the driver creates a cdc-wdm node as well as a network device: autosetup currently assumes this TD Tech path has no cdc-wdm control channel. Do not interpret a Huawei NCM AT control node as proof of MBIM/QMI support.
